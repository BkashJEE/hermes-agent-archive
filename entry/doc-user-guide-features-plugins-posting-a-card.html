Posting a card

From Official Docs · November 28, 2026

Experimental ctx.post_card is experimental, like ctx.fork_session : the card shape and the result codes may change in a later release. Keep the call inside one small function of your plugin that returns plain data. Treat a definite refusal as "no card", but never fall back on an uncertain result as described below. Under plugins.isolation: host a third-party plugin's ctx.post_card and ctx.apost_card exist but raise PluginHostUnsupported (a RuntimeError ), as post_message and fork_session do: the card is admitted on the gateway's event loop into a session the Hermes process owns. A plugin can put a card into a conversation from anywhere, including a timer or its own background thread, without starting a model turn. The card is saved in the session's history, so it is still there after a reload. A card is display-only: people see it, and the model is told only that the plugin posted a card with a core-derived opaque reference (one line, [<plugin id> posted a card <opaque id>] ). The reference is stable for that plugin and card id and saved in the row's content beside its display metadata, so clients can match them.
